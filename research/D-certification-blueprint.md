# D · CCAR-F certification-to-gameplay blueprint

**Baseline · Claude Certified Architect – Foundations, exam code CCAR-F, guide v1.0 effective July 2026. Verified November 12, 2026 from the Anthropic-authored public guide mirrored in the linked repository.**

The guide defines five weighted domains and 30 numbered task statements. Section 6 lists both knowledge and skill bullets under the tasks. The map below uses original summaries of those requirements and gives each task a playable decision, feedback, an unrelated Exam Lens concept and a criterion for independent evidence. The guide's six public scenario categories are support, Claude Code development, multi-agent research, developer productivity, CI and structured extraction. CertCity's proposed locations cover these professional patterns through original problems. The guide specifies 60 items in 120 minutes, single- and multiple-response formats, and four scenario sets drawn from the six. [Anthropic guide, §§3–6 and 8–9](https://github.com/Amey-Thakur/CLAUDE-CERTIFICATIONS/blob/main/architect-foundations/exam-guide.pdf), [Official Partner Academy page](https://anthropic-partners.skilljar.com/claude-certified-architect-foundations-certification)

**Status.** The City Dispatch prototype implements a first module for task 2.2. The mission exercises successful empty results, timeouts, input validation and access denial. The technical debrief adds business-rule handling and shows `isError` separately from application-defined fields. The bike-share and arts-center checks sample these skills through new cases without the workflow diagram or Exam Lens feedback during the questions. Partial-result handoffs across agents are planned under task 5.3. The other 29 tasks remain mapped and planned. [B · Mission design](B-game-design.md), [MCP tool specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

The two scenario forms use separate versioned IDs and score the first complete submission for each form. Earlier prototype scores remain available in practice history. Exam Lens is repeatable practice. Its attempts do not affect either score. The follow-up opens seven days after the first submission on the current form. The static prototype keeps records and answer keys in the browser. Independent item review, authenticated server-held assessment, and learner validation remain release work. [Practice format audit](exam-practice-audit.md) · [G · Evidence plan](G-mvp-plan.md) · [Butler, 2010](https://pubmed.ncbi.nlm.nih.gov/20804289/) · [Cepeda et al., 2008](https://pubmed.ncbi.nlm.nih.gov/19076480/)

**Content acceptance.** For each task, the SME checks the guide's individual knowledge and skill bullets against fixture IDs and evidence IDs. Where a row covers several subskills, the checks should span them over multiple cases, with subskills tracked in metadata. Mark each bullet as taught, practiced, independently sampled, or gap. A domain's exam weight informs full-form sampling. It does not assign points to gameplay. Lens items are original, specify response count, and vary constraints and contexts across families. [Testing Standards](https://www.apa.org/science/programs/testing/standards), [Butler, 2010](https://pubmed.ncbi.nlm.nih.gov/20804289/)

## 1 · Agentic architecture and orchestration · 27% · Guide pp. 5–9

| **1.1 · Agent loop** · `stop_reason`, `tool_use`, `end_turn`, `tool_result` | Continue when the model calls tools, execute permitted calls, append linked results and the model's tool request to history, and stop normally on end turn. A text fragment or fixed iteration cap is an unreliable completion signal. Budgets still bound execution. | Transit lost-property desk. Move trace blocks into a runner, route on the stop reason and reconnect each tool-result ID. | Correct flow completes a compound request. Text-based completion ends early. Dropped results cause repeats or missing facts. | **Single** choose the next transition after a facilities assistant emits text and a tool call together. | Order a new trace and identify the state, correct result ID and next request or stop; recognize an unexpected stop as its own path. |

Serial calls add latency. | **Multiple** identify the missing pieces when a survey-analysis worker lacks the parent evidence and needs independent comparison branches. | Inspect an SDK fixture, authorize the invocation tool, provide complete structured findings, choose parallel grouping and distinguish forks from isolated subagent context. |
| **1.4 · Prerequisites and handoff** · state gate, separate concerns, structured handoff | Enforce verification before an irreversible or sensitive step, split independent concerns and pass a sufficient handoff. A prompt instruction cannot guarantee ordering. | Returns office. Put identity verification upstream of refund, split a two-part ticket, send customer, cause, amount and recommended action to an exception desk. | Unauthorized progression is blocked, independent concerns can proceed, and the receiving worker can resolve the issue. | **Single** select the architecture for a university bursary flow with identity checks and concurrent questions. | Given mixed verified/unverified cases, show both allowed and blocked traces, and choose a handoff sufficient without the original transcript. |
| **1.5 · Tool hooks** · pre-call enforcement, `PostToolUse`, normalization | Intercept before a prohibited call and route to review. Normalize tool output before the model consumes it, including epoch dates and status codes. A post-call hook cannot prevent an already executed action. | Fulfilment office. Place a policy gate and a return-payload adapter on opposite sides of a station. | Out-of-policy change stops before execution; heterogeneous data becomes comparable and fewer records are misread. | **Multiple** place the two controls for a purchase approval system receiving inconsistent supplier timestamps. | Select hook positions and allowed actions, normalize a payload, and show blocked and allowed fixtures against a fixed threshold. |
| **1.6 · Task decomposition** · prompt chaining, adaptive decomposition, local and integration passes | Use fixed stages for predictable work, adaptive tasks for unknown dependencies, and both local and cross-file review for different issue types. A single giant pass can dilute attention. | Release room. Arrange local review benches and integration check. Open a legacy branch that reveals an unexpected dependency and adapt. | Local defects and integration mismatches show up in distinct passes. Extra steps consume time in predictable cases. | **Single** choose a workflow for an incident investigation that changes after initial evidence versus a routine report. | Configure each of two unseen task shapes, preserve cross-component checks and justify the extra stage from evidence. |
| **1.7 · Session lifecycle** · named resume, `--resume`, `forkSession`/`fork_session`, changed files, fresh summary | Resume when context is still valid, branch for independent alternatives, supply targeted changes, and start fresh with verified facts when prior results are stale. | Release room. Check saved investigation cards against file revisions, then resume, fork or start with an updated brief. | Reusing outdated results recommends retired code. Forks preserve original analysis and avoid divergent plans contaminating one another. | **Single** choose the session operation after a pricing service has been refactored or when two designs share a valid baseline. | Match resume/fork/fresh to three unseen histories, select the corresponding CLI or SDK option and list changed artifacts for targeted recheck. |

## 2 · Tool design and MCP integration · 18% · Guide pp. 9–12

| **2.1 · Tool boundaries** · description, schema, examples, overlap, prompt cues | Write clear purpose, inputs, outputs, edge cases and negative boundaries. Configure tool cards and send ambiguous requests through the selector. | Appropriate calls complete on first attempt. Trace a status string through wrappers, find the file and make a localized synthetic patch. | Fewer irrelevant reads and fewer unintended edits. ## 4 · Prompt engineering and structured output · 20% · Guide pp. 16–19

| Task and concepts | Playable competency and misconception | Scenario and mechanic | Consequence | Exam Lens in a different setting | Independent evidence |
|---|---|---|---|---|---|
| **4.1 · Review criteria** · precision, false positives, severity categories | Specify observable report and skip criteria with examples and severity anchors. Pause a noisy class if necessary while measuring why it fails. Vague caution or confidence alone cannot define a defect. | Release room. Tune review criteria cards and run a labeled sample with actual and benign patterns. | True and false findings change, affecting review queue and trust. | **Single** improve an audit reporting legitimate but unusual document formatting as a defect. | Write or select categorical criteria with a boundary example and explain precision/recall tradeoffs on an unseen labeled set. |
| **4.2 · Few-shot examples** · ambiguous boundaries, input variety, output exemplars | Choose a small varied set of examples and demonstrate desired reasoning, format, null handling and edge cases. Repeated easy examples can leave the decision boundary undefined. | Invoice intake. Assemble examples from table, prose and ambiguous source formats and run a held-out batch. | Output format and relevant fields stabilize across layouts. Narrow examples leave new formats brittle. | **Multiple** select examples for a grant workflow with uncertain dates and mixed source layouts. | Choose complementary examples, predict effect on an unseen input and identify an example that encourages hallucination. |
| **4.3 · Structured output** · tool input schema, strict tools, tool choice, required/nullable, enum, semantic invariants | Select a schema and compatible output enforcement, including normalization and extensible unknowns. Guarantee shape where supported and separately verify facts and totals. Forcing a tool on an unsupported model fails. | Invoice intake. Fit schema cards to source variations, route extraction, validate money totals and inspect `tool_use`. | Invalid shape is rejected at the intended layer, missing data stays explicit, plausible wrong values still fail checks. | **Multiple** select schema and validation behavior for receipts with optional tax and inconsistent totals. | Given a specified model configuration, choose `auto`, `any` or a named tool where supported, set field requirements and detect a semantically wrong valid payload. |
| **4.4 · Validation and retry** · actionable feedback, missing data, calculated versus stated totals, `detected_pattern` | Retry a correctable error with source, failed result and specific validator feedback. Route missing or contradictory facts appropriately. Log dismissal patterns to improve criteria. | Invoice intake. Send rejected extracts to targeted repair or review and tag recurring validator failures. | Fixable inconsistencies clear; absent data avoids repeated waste; reviewers see discrepancy evidence. | **Single** choose how to handle a wrong unit format and a source document with an absent measurement. | Distinguish repairable from absent data, assemble a bounded retry payload and expose unresolved discrepancies with a reason. |
| **4.5 · Batch scheduling** · Message Batches, `custom_id`, latency tolerance, partial failures | Select async batch for nonblocking work, synchronous requests for interactive or premerge checks, correlate results by ID, retry failed inputs selectively, and budget schedule plus processing time. The batch cannot pause for an application tool callback mid-request. | Invoice intake. Schedule weekly statements against a deadline, inspect rejected jobs, change only failed inputs and rerun. | Delayed workflows use less inference spend; blocked checks wait too long if sent to batch. | **Single** choose request mode for an immediate approvals screen and a nightly catalog audit. | Compute a schedule buffer from a stated worst-case planning window, join out-of-order outcomes, handle expiry or failure and explain the latency tradeoff. |
| **4.6 · Independent and multi-pass review** · reviewer isolation, local and integration passes, confidence triage | Use an independent review context, focus local passes and verify cross-file behavior. Treat model confidence as an input requiring evaluation. Same-session review can share blind spots. | Release room. Arrange generator, isolated reviewer and integration station, then sample findings. | Subtle errors surface without drowning local review in unrelated context. | **Multiple** choose review changes for a system that misses interface inconsistencies across generated modules. | Design an independent local and integration plan and select how to validate or route findings on an unseen example. |

## 5 · Context management and reliability · 15% · Guide pp. 19–23

| Task and concepts | Playable competency and misconception | Scenario and mechanic | Consequence | Exam Lens in a different setting | Independent evidence |
|---|---|---|---|---|---|
| **5.1 · Critical facts** · persistent case facts, history, compaction, trimming, placement, metadata | Keep precise facts and issue-level IDs outside lossy summaries, carry relevant turn history, trim payloads, organize key findings prominently and preserve metadata. A longer context window alone cannot guarantee recall. | Support case history. Pin date/amount/status fields, trim a raw payload, compact a case and test later resolution. | Correct facts survive the shift; bloated or vague context misroutes cases or loses traceability. | **Multiple** choose changes for a claims assistant losing dates and source page numbers. | Mark minimum necessary fields and metadata, place a compact case block, and resolve an unseen multi-issue case after compaction. |
| **5.2 · Escalation and ambiguity** · explicit human request, exception, frustration, no progress, clarification | Honor explicit human requests promptly, distinguish frustration alone, escalate gaps or stalled cases, and ask for additional identifiers when multiple matches remain. Calibrate with examples. | Support desk. Sort case cards into resolve, clarify or escalate and inspect the handoff. | Escalation load falls without overriding a human request or selecting the wrong account. | **Single** choose the right next action when a customer expressly asks for a human versus when their lookup is ambiguous. | Route paired cases differing by one relevant cue. Explain when frustration, exception, ambiguity or an explicit request changes the route. |
| **5.3 · Multi-agent error propagation** · partial results, coverage, attempted action, local recovery | Recover transient faults at the responsible worker within bounds, then pass structured failure and partial coverage upstream. Successful empty and access failure stay distinct. Avoid silently losing results or aborting unrelated branches. | Research archive or Dispatch extension. Restore one source, attach partial results, annotate coverage on a multi-source workboard. | Coordinator can proceed safely and show gaps. Missing metadata produces false completeness. | **Multiple** select failure-envelope and synthesis changes for an unavailable inspection dataset. | Produce an envelope carrying failure type, attempts, partial results and alternatives, and mark coverage accurately on an unseen trace. |
| **5.4 · Long codebase exploration** · scratchpads, targeted subagents, manifests, `/compact`, recovery | Capture verified files and dependencies, divide specific investigations, pass summaries between contexts and recover from durable state. Generic summaries can lose precise classes and unresolved questions. | Maintenance bench. Split inquiries across toy repo areas, build checkpoint manifest and resume after a staged interruption. | Work resumes from verified findings instead of repeating expensive discovery. | **Single** choose a recovery design for a codebase audit split across several sessions. | Rebuild a new session from a manifest with sources, questions and changed files, and identify which findings need revalidation. |
| **5.5 · Human review and calibration** · field-level confidence, labeled data, stratified audit, thresholds | Calibrate against labels by document and field, send uncertainty and contradictions to humans and audit high-confidence segments. Overall accuracy can hide a failing subgroup. | Invoice intake. Allocate reviewer capacity, stratify high-confidence audits and use a held-out calibration set. | Segment-level failures become visible and high-risk cases reach reviewers. | **Multiple** choose audit and routing changes when aggregate accuracy hides poor handwritten address accuracy. | Interpret a small validation table, choose a field/segment policy, and explain why high-confidence random audits remain necessary. |
| **5.6 · Provenance and uncertainty** · claim-source links, dates, disagreement, evidence presentation | Preserve attribution and methods through handoffs, flag credible conflicts, check time periods and present findings in the appropriate form. A single unlabeled summary can invent consensus. | Research archive. Attach source cards to each claim, compare dates and reconcile or annotate disagreement in the report. | Readers see which claims are verifiable, where evidence diverges and what remains uncertain. | **Single** choose a synthesis strategy when two credible annual counts disagree across collection windows. | Produce a sourced claim pair with publication and collection dates, distinguish real conflict from time mismatch and show uncertainty explicitly. |

## Exam-to-live implementation drift

The guide defines the learning objective. Current docs define the lab implementation. Each fixture stores both versions and a checked-on date. The public guide has no linked technical-doc URIs in the PDF annotations I inspected. Its preparation and appendix sections name technologies and concepts. The domain references above and the API references in [E](E-technical-architecture.md) are the relevant official technical crosswalk. [Guide §§7–8 and 17](https://github.com/Amey-Thakur/CLAUDE-CERTIFICATIONS/blob/main/architect-foundations/exam-guide.pdf)

| Topic | Teach explicitly |
|---|---|
| Agent SDK invocation | The guide uses `Task`. Current SDK docs describe `Agent` in tool-use blocks and `Task` in the initialization list, with older versions using `Task` for both. Lab fixtures label the SDK version and match both names when detecting traces across versions. [SDK subagents](https://code.claude.com/docs/en/agent-sdk/subagents) |
| Hooks | Distinguish decision before execution from output transformation. Current SDK docs describe `updatedToolOutput` and the older MCP-specific `updatedMCPToolOutput`. Pin the lab fixture. [SDK hooks](https://code.claude.com/docs/en/agent-sdk/hooks) |
| Tool choice and strict output | Teach optional, any and named modes under stated compatibility. Several current models reject forced tool choice and manual extended thinking also limits it. Strict tool input and JSON response structure are distinct, and neither verifies business facts. Inspect the latest compatibility table before publishing. [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) |
| Commands, Skills and permissions | Existing command files and Skills share invocation behavior. Prefer Skills for new workflows where their capabilities are useful. In the current Code docs, `allowed-tools` in a Skill preapproves listed tools while active. Enforce the allowed surface through permissions, sandbox and applicable hooks. [Skills](https://code.claude.com/docs/en/skills), [Permissions](https://code.claude.com/docs/en/permissions) |
| Session handling | Match exact interface to the question. Claude Code uses `--resume` and `--fork-session`. SDK options differ by language. Use stable IDs and explicit file-change notes in the lab. [CLI reference](https://code.claude.com/docs/en/cli-reference), [SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions) |
| MCP errors | Application categories and retryability are authored metadata. MCP tool execution errors and protocol errors have different envelopes. Pin the supported MCP revision and show both, keeping the mission focused on a read-only lookup and its recovery policy. [MCP tool spec](https://modelcontextprotocol.io/specification/latest/server/tools) |
