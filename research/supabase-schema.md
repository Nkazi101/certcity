# CertCity Supabase schema

CertCity lets learners explore a shared city, change simulated systems, and practice skills mapped to four certification tracks. A successful city replay changes the learner’s city. It provides a different kind of evidence from a first-seen response or a delayed assessment. City Dispatch has server-committed runs and study checks. Workbench drafts, stakeholder interviews, Exam Lens and general exam practice still use browser progress with account sync. ## What the database needs to preserve

| Product behavior | Schema and reason |
| --- | --- |
| Resume work on another device | `learner_progress` preserves existing versioned saves, including legacy keys. Accounts and guest saves have separate browser namespaces. The browser uploads only the owner’s records and compares revisions before writing. When two devices changed the same save, the learner can choose a copy. |
| Reproduce a scored run after content changes | A track has blueprint versions and content releases. Missions, objective links, prerequisites, forms, items, and fixture definitions are tied to a release. The current-release pointer can move without rewriting prior attempts. The initial catalog is generated from the repository, which remains the authoring source. |
| Replay a shift without double-counting its impact | A mission attempt has a monotonic revision. A run has a unique attempt and command ID, a request hash, the pinned fixture, a policy snapshot, and an evaluation summary. A separate outcome points to the latest accepted run per learner and mission. A failed later run remains in history and preserves the accepted outcome. |
| Preserve the meaning of learning evidence | Forms define intended items, exposures record what the learner actually saw, and responses retain the answer and rubric version. First exposure is unique across forms and releases for a learner and item family. A submitted response and that first exposure are required for an independent evidence row. The scoring service also has to enforce assistance and form rules in the submission transaction. |
| Support cohorts without granting staff access to personal histories | Organizations and cohorts have explicit enrollment. Composite foreign keys prevent assigning someone to a cohort through a different organization’s membership. Staff roles confer no direct access to learner responses or progress. Cohort summaries need a scoped reporting interface and a reporting/consent policy before rollout. |

PostgreSQL enforces identity, version, and membership relationships through primary keys, uniqueness, and foreign keys. JSON holds bounded mechanic-specific content and policies whose shape varies by mission. The owner, content version, action identity, attempt lifecycle, and report dimensions remain relational. The prototype ships answer keys to browsers, so every imported item family is marked `study_only`. New independent families need newly authored material, family assignments reviewed for near duplicates, and a server-only delivery and scoring path. The seeded assessment catalog is a study snapshot. [PostgreSQL constraints](https://www.postgresql.org/docs/17/ddl-constraints.html) · [1EdTech QTI](https://www.1edtech.org/standards/qti) · [Standards for Educational and Psychological Testing](https://www.apa.org/science/programs/testing/standards)

## Request and access boundaries

City Dispatch keeps its browser preview and uses the same deterministic evaluator in a Supabase Edge Function when an account saves a shift. The function validates the caller with Supabase Auth and derives the actor ID from that result. A database transaction locks the owned attempt, checks for a previously committed command, checks the revision, writes the evaluated run, and updates the accepted outcome. A retry of the same request returns the existing run. A different request with that command ID or an outdated revision conflicts. Metrics persist in integer minutes and microcurrency units. [Supabase Edge Function auth](https://supabase.com/docs/guides/functions/auth) · [PostgreSQL row locks](https://www.postgresql.org/docs/17/explicit-locking.html)

After a successful account shift, City Dispatch opens the versioned study form and records item exposures. The submission transaction validates the choices, scores against the stored rubric, and schedules the follow-up 168 hours after the server’s submission timestamp. Concurrent submissions return the first committed result. The server enforces the due time and marks the schedule complete when the follow-up is submitted. Imported browser results stay available under earlier results when a learner starts the server-scored sequence. The Dispatch questions remain study-only because they were already published to browsers.

Learners can read their own progress and authoritative run summaries through row-level security. Browser clients can update their own prototype saves and profile fields. Authenticated clients have no write grants on outcomes or evidence. Raw responses, rubrics, fixtures and simulation events are in a private schema. Account deletion through Auth cascades to learner records via foreign keys. A user-facing deletion workflow and local cache removal still need implementation before pilot enrollment. [Supabase row-level security](https://supabase.com/docs/guides/database/postgres/row-level-security) · [Supabase user management](https://supabase.com/docs/guides/auth/managing-user-data)

## Growth and operating limits

Indexes follow the initial access paths. Learner dashboards query by owner and time. A due-date index targets incomplete follow-ups. The command lock is scoped to one attempt, so unrelated saves can proceed concurrently. Store one aggregate outcome per mission and keep detailed traces off the public read path. Load testing, query plans, retained trace volumes, and retention requirements should determine when event partitions or materialized reporting are warranted. The project’s modeled learner counts are planning assumptions.
